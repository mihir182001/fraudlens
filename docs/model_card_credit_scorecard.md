# Model Card: FraudLens Credit Risk Scorecard

Registered name: `fraudlens_credit_scorecard` (MLflow Model Registry, alias `champion`, version 4)
Served from: `models/credit_scorecard.joblib`
Trained by: `src/serving/train_serving_models.py` (`train_credit_serving_scorecard`)

## 1. What this model does

Scores a credit application and returns three things: a points-based
scorecard score, the underlying model's default probability, and a decision
(`approve`, `review`, or `decline`) from a separate, explicit thresholding
layer (`src/serving/decision_policy.py`). Served over HTTP by `POST
/score/credit` (`src/api/main.py`).

## 2. Intended use

Scoring a credit application from the applicant's own stated attributes,
with no transaction history required (unlike the fraud model). A caller
sends the raw application fields listed in `CreditScoringRequest`
(`src/serving/schemas.py`); every field is optional, and a field genuinely
absent from a real application is meaningful data the scorecard is built to
handle (see Section 4), not an error.

This model is not intended, and has not been evaluated, for any use beyond
scoring applications shaped like the Home Credit Default Risk dataset's own
schema (see Training Data below).

## 3. Training data

**Real data.** This version is trained on the real Home Credit Default Risk
Kaggle competition file (`application_train.csv`), loaded by
`src/data/load_credit_applications.py`, which subsets the real file's 122
columns down to the same 18-column schema this project's serving API
(`CreditScoringRequest`) already accepts, so the rest of the pipeline (WoE
encoding, the points scorecard) runs unchanged against real values. This
replaces the synthetic data this project used earlier in development,
generated by `src/data/generate_synthetic_credit.py` (still available as
this training function's default when no real CSV path is given, for fast
local iteration without the real file present).

This run (the exact command in Section 8 reproduces it):

| Quantity | Value |
|---|---|
| Data source | Real Home Credit Default Risk Kaggle file, subset to this project's 18-column schema |
| Total applications | 307,511 |
| Realized default rate | 8.07% (24,825 of 307,511) |
| Train rows | 246,008 |
| Test rows | 61,503 |
| `EXT_SOURCE_1` missing rate | 56.38% |
| `EXT_SOURCE_2` missing rate | 0.21% |
| `EXT_SOURCE_3` missing rate | 19.83% |
| `DAYS_EMPLOYED` anomaly rate | 18.01% |

The `DAYS_EMPLOYED` anomaly rate is the real share of applicants recorded
with `DAYS_EMPLOYED = 365243`, the real dataset's own documented placeholder
for unemployed, retired, and pensioner applicants rather than a real
employment length (one of the most commonly discussed data-quality artifacts
in public analyses of this competition). This project's WoE encoder
(Section 4) gives that placeholder value its own explicit bin rather than
averaging it into "long employment," a design decision made before real
data was available specifically so this exact real anomaly would be handled
correctly once it was.

## 4. Model architecture

A logistic regression fit on Weight-of-Evidence (WoE) encoded features
(`src/credit_risk/woe_encoding.py`, `src/credit_risk/scorecard_model.py`),
converted into a points-based scorecard using the standard Offset/Factor
transformation (Naeem Siddiqi's "Credit Risk Scorecards", the
industry-standard reference for this exact conversion). A logistic
regression on WoE-encoded features is used specifically because it is the
only common model type whose linear score decomposes into fixed
per-feature-bin point contributions; that additive structure is what makes
a points-based scorecard (computable by hand, or a lookup table, without a
live model call) possible at all. A tree ensemble's output has no
equivalent decomposition, which is why this project uses XGBoost for the
fraud model but a WoE logistic regression here (see
`scorecard_model.py`'s own docstring for the full reasoning and the exact
points formula).

From the 18 raw application features, feature selection by Information
Value (`select_features_by_iv`, minimum IV of 0.02) keeps 12 on this real
run: `EXT_SOURCE_3`, `EXT_SOURCE_2`, `EXT_SOURCE_1`, `DAYS_EMPLOYED`,
`DAYS_BIRTH`, `NAME_INCOME_TYPE`, `NAME_EDUCATION_TYPE`, `CODE_GENDER`,
`AMT_GOODS_PRICE`, `AMT_CREDIT`, `REGION_RATING_CLIENT`,
`NAME_FAMILY_STATUS`. The three `EXT_SOURCE` bureau-score features again
rank highest by IV, matching what public analyses of the real competition
consistently report as its three strongest predictors. Every feature is
binned into 5 WoE bins (`fit_woe_bins`, fit on the train split only), with
`DAYS_EMPLOYED`'s 365243 anomaly value given its own explicit bin rather
than being pooled with real employment lengths.

The points conversion uses `pdo=20`, `base_score=600`, `base_odds=50`
(points to double the odds, and an anchor score/odds pair). These are
illustrative conventions this project chose, not a universal standard;
different institutions anchor the same formula differently. Because the
scorecard score is a strictly monotonic transform of the logistic
regression's own predicted probability, every ranking metric below (AUC-ROC,
AUC-PR, KS, Gini) is identical whether computed on the points score or the
raw probability; the scorecard changes what a business user reads, not what
the model can discriminate (confirmed directly, see
`tests/test_scorecard_model.py`).

## 5. Performance (test set, this exact run)

| Metric | Value |
|---|---|
| AUC-ROC | 0.7374 |
| AUC-PR | 0.2040 |
| KS statistic | 0.3649 |
| Gini coefficient | 0.4747 |

These numbers come from running `train_credit_serving_scorecard` with
`--credit-csv` pointed at the real, downloaded `application_train.csv`
(307,511 real applications, 24,825 real defaults, subset to this project's
18-column schema; 61,503 of those applications in this run's test split),
reproduced directly while writing this update (see Section 8). AUC-PR is
lower than AUC-ROC here for the expected reason: precision-recall metrics
are sensitive to class imbalance, and defaults are 8.07% of this real
population. These real numbers are close to this project's earlier
synthetic-data run (AUC-ROC 0.7390 synthetic vs. 0.7374 real; Gini 0.4780
synthetic vs. 0.4747 real), which is a reassuring sign that the synthetic
generator's calibration (see `generate_synthetic_credit.py`'s own module
docstring) was a reasonably faithful stand-in for this particular model's
discriminative power on this dataset. That is an observation about this one
comparison, not a general guarantee that synthetic and real performance
will always match this closely.

## 6. Decision policy

`src/serving/decision_policy.py` converts the scorecard points score into a
decision using two cutoffs, both percentiles of this run's own TRAIN split
score distribution (never test, never live traffic):

| Cutoff | Value | Decision |
|---|---|---|
| `approve_cutoff` (60th percentile) | 573.3 | `approve` at or above |
| `decline_cutoff` (20th percentile) | 544.0 | `decline` below; `review` between |

These are illustrative choices for this project, not a claim about any real
institution's actual risk appetite or a regulator-reviewed cost-benefit
analysis (see `decision_policy.py`'s own docstring for the full reasoning
and caveats). These cutoffs are close to, but not identical to, the earlier
synthetic-data run's (579.2 approve / 543.4 decline), consistent with how
close the two runs' overall score distributions turned out to be (Section 5).

Every `CreditScoringRequest` field is optional; a missing value is passed
through to the WoE encoder, which has its own explicit `MISSING_LABEL` bin
for exactly this case (the same handling `EXT_SOURCE_1` and
`DAYS_EMPLOYED`'s real, disclosed missingness already exercises in
training).

## 7. Monitoring: automated PSI drift detection

Unlike the fraud model, this scorecard has a standalone, automatable drift
check: `src/credit_risk/monitor_psi.py`. It loads the exact artifact being
served (`models/credit_scorecard.joblib`), scores a new batch of
applications against it (a real CSV via `--input-csv`, or a disclosed
synthetic batch by default), and computes the Population Stability Index
(PSI) between that batch's scores and `reference_scores`, the scorecard's
own test-set scores saved at training time (now 61,503 real test-set
scores, rather than the earlier 1,600 synthetic ones; see
`src/credit_risk/psi_monitoring.py` for the PSI formula and interpretation
bands). It logs each run to the `fraudlens_credit_scorecard` MLflow
experiment (the same one the project's dashboard reads its PSI history
from) and exits non-zero on a `significant_shift` verdict (PSI >= 0.25), so
it can be wired into a scheduled job or CI workflow that alerts on that exit
code.

Run it with:
```
python -m src.credit_risk.monitor_psi
```

A per-feature PSI breakdown (which raw input drove a shift) is a separate,
manual step: `train_scorecard.py`'s own PSI demonstration computes this
against a full reference population; `credit_scorecard.joblib` itself only
stores the reference SCORES, not the full reference feature dataframe, so
this script's own score-level PSI is the automatable, alertable signal, and
a full root-cause breakdown remains a manual follow-up when it fires.

## 8. Reproducing this card's numbers

```
python -m src.serving.train_serving_models --credit-csv path/to/application_train.csv
```

pointed at the real, downloaded Home Credit file trains this exact model
(and, if `--transaction-csv`/`--identity-csv` are also given, the fraud
model; see the companion model card) and writes
`models/credit_scorecard.joblib`. The train/test split for this real-data
path uses a fixed `random_state=0` inside `train_test_split` regardless of
the `--seed` flag (the `--seed` flag only affects the synthetic-data code
path used when `--credit-csv` is omitted), so re-running against the same
real file should reproduce the printed `test AUC-ROC`, `approve_cutoff`,
and `decline_cutoff` exactly. Unless `--skip-registry` is passed, this also
registers a new version of `fraudlens_credit_scorecard` in the MLflow Model
Registry and promotes it to the `champion` alias
(`src/serving/model_registry.py`); this card's numbers come from registered
version 4.

## 9. Known limitations

- The real data used here is the full public `application_train.csv`
  Kaggle competition training file, split into this run's own train/test
  portions. These numbers are this project's own internal validation split
  of that file, not a benchmark against Kaggle's separate, official private
  leaderboard test set (`application_test.csv`), which has no public labels
  and was not used here.
- The real Home Credit dataset has 122 columns; this project's schema keeps
  only the 18 most commonly analyzed in public write-ups (Section 3), so
  feature interactions the real, fuller schema might reveal are untested
  here.
- AUC-PR (0.2040) reflects a genuinely simple, 12-feature linear model on
  real bureau-score and demographic fields; it should not be read as a
  ceiling on what a scorecard could achieve on this dataset with more
  careful feature engineering or a wider column set.
- Decision cutoffs are train-set score percentiles, an illustrative
  business-policy stand-in, not a cost-benefit-calibrated or
  regulator-reviewed threshold.
- The PSI monitoring script (Section 7) checks only the final score's
  distribution; it does not by itself identify which raw feature is
  driving a detected shift without a separate, manual
  `psi_by_feature` run.
