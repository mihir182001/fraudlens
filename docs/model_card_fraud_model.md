# Model Card: FraudLens Fraud Detection Model

Registered name: `fraudlens_fraud_model` (MLflow Model Registry, alias `champion`, version 4)
Served from: `models/fraud_model.joblib`
Trained by: `src/serving/train_serving_models.py` (`train_fraud_serving_model`)

## 1. What this model does

Scores a single credit card transaction and returns a probability that the
transaction is fraudulent, together with a decision (`approve`, `review`, or
`decline`) produced by a separate, explicit thresholding layer
(`src/serving/decision_policy.py`). The model itself never returns a decision;
it returns a probability, and the decision policy applies a business
threshold on top of it, so the two can be reasoned about and tested
independently. Served over HTTP by `POST /score/fraud`
(`src/api/main.py`).

## 2. Intended use

Scoring already-engineered transaction feature vectors at inference time, in
a stateless HTTP request. It is not intended to take raw transaction fields
directly: several of its own features (velocity counts, running averages,
frequency encodings) require historical state across many prior
transactions for the same card, which a single stateless request does not
carry. A real deployment would compute these features in an upstream
feature-serving layer and hand this model the finished vector, exactly as
`FraudScoringRequest` expects (see `src/serving/schemas.py`). `GET
/models/fraud/schema` reports the exact feature names and count the
currently loaded model expects.

This model is not intended, and has not been evaluated, for any use beyond
scoring transactions shaped like the IEEE-CIS Fraud Detection dataset's own
schema (see Training Data below).

## 3. Training data

**Real data.** This version is trained on the real IEEE-CIS Fraud Detection
Kaggle competition files (`train_transaction.csv` and `train_identity.csv`),
loaded and merged by `src/data/load_and_merge.py` and passed through this
project's existing, schema-agnostic feature pipeline
(`src/models/prepare_model_data.py`) unchanged. This replaces the synthetic
data this project used earlier in development, generated by
`src/data/generate_synthetic_ieee.py` (still available as this training
function's default when no real CSV paths are given, for fast local
iteration without the real files present).

This run (the exact command in Section 7 reproduces it):

| Quantity | Value |
|---|---|
| Data source | Real IEEE-CIS Fraud Detection Kaggle files |
| Total transactions | 590,540 |
| Realized fraud rate (whole dataset) | 3.50% (20,663 of 590,540) |
| Train rows | 472,432 |
| Test rows | 118,108 |
| Identity match coverage | 24.42% of transactions |
| Feature columns | 417 |

Per-split fraud counts (train vs. test) were not separately measured for
this card; the dataset-level rate above, and the chronological split
described below, are what this run and its reproduction script directly
measured.

The 417 feature columns are not a hand-curated list: `select_feature_columns`
(`src/models/prepare_model_data.py`) auto-detects every numeric or boolean
column present in the merged, feature-engineered data, rather than hardcoding
column names, which is exactly why this project's existing pipeline needed no
code changes to run against the real file's full column set (393 raw
`train_transaction.csv` columns plus identity columns, versus the reduced
~20-column synthetic stand-in used earlier). The same engineered features
this project has always computed still apply on top of the raw columns:
per-card transaction velocity and running spend statistics
(`card1_txn_count_1h`, `card1_amt_sum_1h`, `card1_txn_count_1d`,
`card1_amt_sum_1d`, `card1_prior_txn_count`, `card1_running_avg_amt`,
`card1_amt_ratio_to_own_avg`, `card1_prior_distinct_addr1_count`),
hour-of-day aggregates (`hour_of_day_avg_amt`, `hour_of_day_txn_count`),
frequency encodings of categorical columns (`ProductCD_freq`, `card4_freq`,
`card6_freq`, `P_emaildomain_freq`, `R_emaildomain_freq`), and a binary
identity-match flag (`has_identity_match`). The real dataset's own documented
missingness in columns such as `dist1`, `dist2`, and several `D`-family
columns is handled by the model's own imputer (see Section 4); `null` in an
API request encodes the same missingness (see Section 6).

The train/test split is chronological (`prepare_train_test_features`),
not a random shuffle, so the model is always evaluated on transactions that
occur later in the real dataset's own timeline than everything it was
trained on. This split needs no random seed (it sorts by time and slices),
so it reproduces identically given the same input files.

## 4. Model architecture

XGBoost (`XGBClassifier`), trained inside an `imblearn.pipeline.Pipeline`
with two steps ahead of the model: a `SimpleImputer` (median strategy, fit
on train only) and SMOTE (Synthetic Minority Oversampling Technique,
applied to the training data only; `imblearn`'s pipeline knows to skip
resampling at prediction time, so the test set is never touched by SMOTE).
See `src/models/advanced_models.py` for the full pipeline definition. Both
SMOTE and XGBoost use a fixed `RANDOM_STATE = 42` internally, so re-running
this exact pipeline against the same real CSV files reproduces the same
fitted model.

This serving artifact deliberately uses XGBoost's library-default
hyperparameters (no `RandomizedSearchCV` tuning), a choice made to keep
this specific script fast and deterministic for repeated local retraining,
not a claim that untuned is the project's best-performing configuration.
`src/models/advanced_models.py`'s own hyperparameter-tuned runs remain the
project's separate research benchmark (evaluated on synthetic data); this
serving artifact reports its own, real, untuned numbers rather than
borrowing that benchmark's.

## 5. Performance (test set, this exact run)

| Metric | Value |
|---|---|
| AUC-ROC | 0.8875 |
| AUC-PR | 0.4948 |
| KS statistic | 0.6260 |
| Gini coefficient | 0.7749 |

These numbers come from running `train_fraud_serving_model` with
`--transaction-csv`/`--identity-csv` pointed at the real, downloaded
`train_transaction.csv`/`train_identity.csv` (590,540 real transactions,
20,663 real fraud cases; 118,108 of those transactions in this run's test
split), reproduced directly while writing this update (see Section 7). This
real run's AUC-ROC (0.8875) is meaningfully lower than this project's
earlier synthetic-data run (0.9863), and AUC-PR (0.4948) is well below the
earlier synthetic 0.8561: real fraud is a harder, noisier problem than the
clean, calibrated synthetic stand-in this project used before real data was
available, and this gap is expected, not a sign of a bug. The earlier
synthetic numbers should no longer be treated as this model's expected
performance; the numbers in this section are what the model actually
achieves on real, held-out transactions from the same competition's
training data (see Section 9 for the caveat about that vs. Kaggle's own
private leaderboard).

## 6. Decision policy

`src/serving/decision_policy.py` converts the raw probability into a
decision using two thresholds, both derived from this run's own test set
via `optimal_threshold_by_f1` (`src/models/metrics.py`):

| Threshold | Value | Decision at or above |
|---|---|---|
| `review_threshold` | 0.3366 | `review` |
| `decline_threshold` | 0.6683 | `decline` |

`review_threshold` is the F1-optimal cut point on this model's own real test
set. `decline_threshold` is set halfway between `review_threshold` and 1.0,
on the reasoning that only the most confident fraud predictions should be
auto-blocked without a human look. Both are illustrative choices for this
project, not a claim about any real institution's actual risk appetite or a
regulator-reviewed cost-benefit analysis (see `decision_policy.py`'s own
docstring for the full reasoning and caveats). Note that `review_threshold`
(0.3366) is noticeably lower here than in the earlier synthetic-data run
(0.5650), a direct consequence of the real data's own severe class
imbalance (3.50% fraud) shifting where the F1-optimal cut point on
probability actually falls.

`optimal_threshold_by_f1` is computed on the same test set the headline
metrics above are reported on, not a separate validation split; this
project's own known limitation (see `advanced_models.py`'s docstring) is
that this threshold should be read as "the best threshold in hindsight on
this test set," not an unbiased estimate for transactions the model has
never seen.

A request's `features` dict is typed to accept `null` for any individual
feature value. The API converts each `null` to a real `float("nan")` before
scoring, so a legitimately missing engineered feature (`dist1`, `dist2`,
some `D`-family columns) reaches the model's imputer exactly the way it did
during training. A feature key must still be present in the request; only
its value may be `null`.

## 7. Reproducing this card's numbers

```
python -m src.serving.train_serving_models \
    --transaction-csv path/to/train_transaction.csv \
    --identity-csv path/to/train_identity.csv
```

pointed at the real, downloaded IEEE-CIS files trains this exact model (and,
if `--credit-csv` is also given, the credit scorecard; see the companion
model card) and writes `models/fraud_model.joblib`. The chronological split
needs no random seed, and SMOTE/XGBoost both use a fixed internal
`RANDOM_STATE = 42` (Section 4), so re-running against the same real CSV
files should reproduce the printed `test AUC-ROC`, `review_threshold`, and
`decline_threshold` exactly. Running the same command with no `--transaction-csv`/
`--identity-csv` flags instead retrains on synthetic data at this function's
defaults, useful for fast local iteration without the real files present,
but produces different numbers than this card reports. Unless
`--skip-registry` is passed, this also registers a new version of
`fraudlens_fraud_model` in the MLflow Model Registry and promotes it to the
`champion` alias (`src/serving/model_registry.py`); this card's numbers come
from registered version 4.

## 8. Monitoring

This model does not currently have an automated drift-monitoring script
analogous to `src/credit_risk/monitor_psi.py` (the credit scorecard's PSI
check). `src/models/metrics.py`'s KS statistic and Gini coefficient are
computed at every training run and are the metrics to watch for
degradation across retrains; building a fraud-model equivalent of the
credit scorecard's automated PSI check is a natural next extension, not yet
built.

## 9. Known limitations

- The real data used here is the full public `train_transaction.csv`/
  `train_identity.csv` Kaggle competition training files, split
  chronologically into this run's own train/test portions. These numbers
  are this project's own internal, held-out-in-time validation, not a
  benchmark against Kaggle's separate, official private leaderboard test
  set (`test_transaction.csv`/`test_identity.csv`), which has no public
  labels and was not used here.
- Feature engineering (velocity counts, running averages, frequency
  encodings) is computed the same way regardless of data source, but was
  originally spot-checked for correctness on a much smaller synthetic
  sample; no correctness issue is known running it at the real dataset's
  590,540-row scale, but it has not been separately, exhaustively audited
  at that scale.
- The decision threshold is picked in hindsight on the same test set that
  reports the headline metrics (Section 6); an unbiased threshold estimate
  needs a third, held-out split.
- No per-feature drift monitoring is wired up yet (Section 8); this matters
  more now that the model trains on real data, where real-world drift is an
  actual future risk rather than a synthetic-generator hypothetical.
- Skops (MLflow's model serialization) requires an explicit trusted-types
  list for this model's pipeline shape (SMOTE plus XGBoost) to reload
  correctly; that list is maintained in
  `src/models/advanced_models.SKOPS_TRUSTED_TYPES` and reused wherever this
  model is registered. A future change to SMOTE's or XGBoost's internal
  object types could require updating that list.
